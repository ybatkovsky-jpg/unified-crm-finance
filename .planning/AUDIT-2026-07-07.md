**Файл:** `apps/web/src/lib/auth/jwt.ts:4`
```typescript
const SECRET = new TextEncoder().encode(
```

## 3. Высокий приоритет (HIGH)

### 🔴 H1 — 74 API-роута без проверки сессии
**Файлы:** `deliveries/route.ts`, `categories/route.ts`, `counterparties/route.ts`, `contracts/route.ts`, `budgets/route.ts`, `lead-sources/route.ts`, `finance/debts/route.ts`, `finance/summary/route.ts`, `accounting/pnl/route.ts`, `accounting/cashflow/route.ts`, `accounting/plan-fact/route.ts`, `purchase-requests/route.ts`, `files/route.ts`, `webhooks/route.ts`, и многие другие.

Middleware проверяет только валидность JWT (подпись + expiry), но **не проверяет** `isActive` и `deletedAt` пользователя. Деактивированный пользователь сохраняет доступ на 7 дней (пока жив JWT).

**Исправление:** Перенести `getSession()` в middleware или добавить request-scoped кеш сессии.

### 🔴 H2 — GET-by-ID без проверки владельца (IDOR на чтение)
| Эндпоинт | Файл | Проверка на GET? |
|---|---|---|
| `GET /api/deals/[id]` | `deals/[id]/route.ts:28-100` | ❌ |
| `GET /api/contacts/[id]` | `contacts/[id]/route.ts:19-35` | ❌ |
| `GET /api/projects/[id]` | `projects/[id]/route.ts:31-119` | ❌ |
| `GET /api/transactions/[id]` | `transactions/[id]/route.ts:30-64` | ❌ |
| `GET /api/interactions/[id]` | `interactions/[id]/route.ts:30-58` | ❌ |
| `GET /api/approvals/[id]` | `approvals/[id]/route.ts:14-33` | ❌ |
| `GET /api/files/[id]` | `files/[id]/route.ts:31-86` | ❌ (генерирует presigned URL для любого файла) |

PATCH/DELETE на тех же роутах **проверяют** владельца. GET — нет. Любой аутентифицированный пользователь может читать любые сущности перебором ID.

**Исправление:** Добавить `canModify(session, existing.managerId === session.id)` во все GET-by-id.

### 🔴 H3 — Нет rate limiting
`.env.example:92-93` определяет `RATE_LIMIT_PER_MIN=100` и `RATE_LIMIT_AUTH_PER_MIN=5`, но **ни одной строчки кода** не использует эти переменные. Брутфорс логина, перебор API, загрузка файлов — без ограничений.

**Исправление:** Внедрить `@upstash/ratelimit` с Redis или in-memory ratelimit хотя бы на `/api/auth/login` и `/api/files`.

### 🔴 H4 — `Deal.moveStage()` — 3 неатомарных записи
**Файл:** `apps/web/src/lib/db/deals.ts:182-250`
```typescript
await prisma.dealHistory.create({ ... })  // Шаг 1
await prisma.deal.update({ ... })         // Шаг 2
if (isWonOrLost) {
  await prisma.deal.update({ ... })       // Шаг 3 — отдельно
}
```
Если шаг 2 или 3 упадёт — история уже записана. Данные рассогласованы.

**Исправление:** Обернуть все три в `prisma.$transaction([...])`.

### 🔴 H5 — N+1 запросов
- `finance/summary/route.ts:95-110` — агрегация по 5 категориям в цикле (5 запросов вместо одного `groupBy`)
- `purchase-requests.ts:193` — `groupBOMBySupplier()` дёргает `counterparty.findUnique` для каждого поставщика в цикле
- `task-templates.ts:231` — `materializeInstances()` запрашивает существующие инстансы по одному на каждый шаблон

### 🔴 H6 — Нет пагинации на list-эндпоинтах
**Все list-эндпоинты** (deals, contacts, projects, contracts, budgets, categories, counterparties, deliveries, purchase-requests, invoices) возвращают **весь набор данных** без `take`/`skip`. Тип `PaginationOptions` существует в `lib/api/types.ts:53-56`, но не используется.

**Исправление:** Добавить `?skip=&take=` во все list-роуты. Использовать существующий `PaginationOptions`.

### 🔴 H7 — Конкурирующие синглтоны Prisma
**Файлы:** `lib/db/prisma.ts` (46 строк) и `lib/db.ts` (20 строк). Оба создают `PrismaClient`, оба пишут в `globalThis.prisma`. Какой «победит» — зависит от порядка импортов. Это латентный баг.

**Исправление:** Удалить `lib/db.ts`. Оставить только `lib/db/prisma.ts`.

## 4. Средний приоритет (MEDIUM)

### 🟡 M1 — Отсутствует сервисный слой (Service Layer)
API-роуты вызывают репозитории напрямую и **руками мапят** Prisma-сущности в API-форму. Например, `deals/route.ts:59-70`:
```typescript
const data = deals.map((d) => ({
  ...d,
  stage: d.DealStage ? { id: d.DealStage.id, name: d.DealStage.name, ... } : undefined,
  manager: d.Manager ? { id: d.Manager.id, name: d.Manager.name, email: d.Manager.email } : undefined,
  // ...
}))
```
Этот маппинг дублируется в каждом роуте (deals, projects, contacts, tasks…). Нет единого DTO-слоя.

**Рекомендация:** Ввести `src/lib/services/` слой с методами типа `DealService.list()`, `DealService.getById()`. Сервис принимает сырые параметры, вызывает репо, мапит в DTO, возвращает готовый ответ. Роут становится тонким: «принять запрос → вызвать сервис → вернуть ответ».

### 🟡 M2 — Нет валидации через schema-библиотеку
Ни одного использования Zod, Yup, или TypeBox. Валидация — ручная (`if (!body.title)` в каждом роуте). Качество варьируется:
- `contacts/route.ts:38-86` — regex для телефона, email, ИНН, КПП, ОГРН (хорошо)
- `deliveries/route.ts:33` — `!body.projectId \|\| !body.supplierId` (плохо)

**Рекомендация:** Внедрить Zod. Один раз описать схему — использовать и для валидации в API, и для типов в `lib/api/types.ts`.

### 🟡 M3 — Непоследовательная обработка ошибок
- `mapErrorToResponse()` (из `lib/api/error-mapping.ts`) используется в ~3 роутах
- ~10 роутов реализуют **свой** маппинг ошибок через `message.includes('...')`
- ~40 роутов просто возвращают `{ error: 'Internal Server Error' }, 500`
- `PurchaseRequestRepository` **переопределяет** `NotFoundError` и `ValidationError` локально вместо импорта из `./errors`

**Рекомендация:** Сделать `mapErrorToResponse` единым стандартом. Обернуть все роуты в `try { ... } catch (e) { return mapErrorToResponse(e) }`.

### 🟡 M4 — Монолитный файл типов (1500+ строк)
`lib/api/types.ts` — 1504 строки, все DTO для всех доменов в одном файле.

**Рекомендация:** Разбить на `lib/api/types/deals.ts`, `lib/api/types/projects.ts` и т.д. Экспортировать через barrel-файл.

### 🟡 M5 — Файловый аплоад доверяет клиентскому `uploadedBy`
**Файл:** `src/app/api/files/route.ts:54`
```typescript
const uploadedBy = (formData.get('uploadedBy') as string) || null
```
Клиент может подставить любой userId. DELETE проверяет `session.id`, а POST — нет.

**Исправление:** `const uploadedBy = session.id`. Игнорировать formData.get('uploadedBy').

### 🟡 M6 — `createdBy: 'system'` в transactions
**Файл:** `src/app/api/transactions/route.ts:126`
```typescript
createdBy: body.createdBy ?? 'system'
```
Таски уже починили (tasks/route.ts:131 — комментарий «раньше 'system' — несуществующий FK»), а транзакции — нет. `'system'` — невалидный FK.

**Исправление:** `createdBy: session.id`.

### 🟡 M7 — 14 моделей без индекса на `deletedAt`
Модели: Deal, Contract, Counterparty. Каждый `findMany` добавляет `WHERE deletedAt IS NULL`, но индекса нет → на больших таблицах будет seq scan.

**Исправление:** Добавить `@@index([deletedAt])` в Prisma-схему + миграцию.

### 🟡 M8 — 4 модели без FK-ограничений
- `CashFlowPayment.invoiceId` — String без relation к Invoice
- `Transaction.createdBy` — String без relation к User
- `ClassificationRule.projectId` — String без relation к Project
- `EventRecurrence.createdBy` — String без relation к User

**Исправление:** Добавить Prisma-relations + FK-миграции.

### 🟡 M9 — `analyticsManagerScope()` c хардкод-списком ролей
**Файл:** `src/lib/auth/analytics-rbac.ts:30`
```typescript
const managerRoles = ['director', 'technologist', 'supply', 'accountant']
```
Список не синхронизирован с `ROLE_MATRIX` из `roles.ts`. Если в матрицу добавят новую роль с `viewAllProjects` — аналитика её не учтёт.

## 6. Архитектурные рекомендации

### 🏗️ R1 — Внедрить Service Layer
```
Текущее:   Route → Repository → Prisma
Целевое:   Route → Service → Repository → Prisma
                        ↘ DTO mapping
                        ↘ Validation (Zod)
                        ↘ Business logic
```
Роут становится 10-строчным: принять параметры, вызвать `service.method(params)`, вернуть `NextResponse.json(result)`.

### 🏗️ R2 — Внедрить Zod для валидации + генерации типов
```typescript
// lib/validations/deal.schema.ts
export const createDealSchema = z.object({
  title: z.string().min(1).max(200),
  amount: z.number().positive().optional(),
  pipelineId: z.string().uuid(),
  stageId: z.string().uuid(),
})
export type CreateDealInput = z.infer<typeof createDealSchema>

// В роуте:
const body = createDealSchema.parse(await request.json())
```
Одна схема = валидация + тип + документация.

### 🏗️ R3 — Перейти на React Server Components (Next.js 16)
Вместо 48 `"use client"` страниц с `useState`/`useEffect`:
```typescript
// app/(app)/deals/page.tsx (Server Component)
export default async function DealsPage() {
  const deals = await dealsService.list() // прямой вызов БД, без HTTP
  return <DealsList data={deals} />
}
```
Интерактивные части (фильтры, drag-drop) — в отдельных Client Components.

### 🏗️ R4 — Внедрить SWR или React Query для клиентских запросов
Вместо ручного `useState([data, loading, error])` + `useEffect`:
```typescript
const { data, error, isLoading } = useSWR('/api/deals', dealsApi.list)
```
Автоматический кеш, ревалидация, дедупликация, optimistic updates.

### 🏗️ R5 — Единый формат ответа API
Стандартизировать все ответы:
```typescript
// Успех
{ "data": T | T[], "meta"?: { count, page, totalPages } }

// Ошибка
{ "error": "VALIDATION_ERROR", "message": "...", "details"?: [...] }
```
Убрать разнобой: `{ user }`, `{ ok: true }`, `{ data, summary }`, `{ status, services }`.

### 🏗️ R6 — Общий пакет типов между web и worker
Создать `packages/shared-types/` с Prisma-генерированными типами + Zod-схемами. Worker (Python) может использовать JSON Schema, сгенерированную из Zod.
