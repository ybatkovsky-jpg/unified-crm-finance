# 04. Техническая реализация генерации пакета документов

**Ключевое решение (по владельцу системы):** пакет документов генерируется **на этапе создания проекта**, т.е. при переходе сделки на этап воронки «договор заключён», когда в системе создаётся проект с номером вида `ПМ2026-000001` (по ТЗ: «при переходе сделки на этап воронки договор заключен формируются договора и создается очередной проект»).

**Наборы форм (05-Б):** потребительские формы (физлица) — по существующим образцам `documents/`; для юрлиц и ИП — отдельные B2B-редакции (разрабатываются, 03 §4).

---

## 1. Событийная модель генерации

Документы делятся на две группы по моменту, когда известны их данные:

| Группа | Документы | Когда генерируется |
|---|---|---|
| **Базовая (при создании проекта)** | ДКП, Договор на монтаж\*, БЗ, СП, Памятка, Правила (черновик), ГТ (черновик с пустыми датами передачи) | событие `project.created` (стадия сделки «договор заключён») |
| **Событийная (позднее)** | Акт приёма-передачи Товара (при передаче), Акт выполненных работ (по завершении монтажа), финальные версии ГТ/Правил с датой передачи | события `goods.transferred`, `installation.finished` |

\* Договор на монтаж и АВР включаются в пакет только при `Order.hasAssembly = true`.

**Реализация:** в CRM вешается обработчик на смену стадии сделки/создание проекта → формируется «снапшот» данных (см. п. 5) → запускается генератор → готовые файлы сохраняются в проект и собираются в архив. Документы событийной группы генерируются аналогично по своим событиям и **дописываются в тот же пакет** (обновление файлов проекта), перекрёстные ссылки (№ ДКП и пр.) берутся из снапшота проекта, чтобы номера не разъезжались.

## 2. Состав пакета (правило сборки)

Пакет = набор файлов проекта, именуемых по шаблону `{номер_проекта}_{тип}.{ext}`:

```
ПМ2026-000001_sale-contract.docx        (ДКП)
ПМ2026-000001_order-form.xlsx           (БЗ)
ПМ2026-000001_specification.xlsx        (СП)
ПМ2026-000001_memo.docx                 (Памятка)
ПМ2026-000001_warranty.docx             (ГТ)          — при передаче товара
ПМ2026-000001_usage-rules.docx          (Правила)
-- только если Order.hasAssembly:
ПМ2026-000001_assembly-contract.docx    (ДМ)
ПМ2026-000001_works-act.docx            (АВР)         — по завершении монтажа
-- событие передачи товара:
ПМ2026-000001_goods-transfer-act.docx   (АПП)
```

Итог — ZIP `ПМ2026-000001_docs.zip` (или папка в проекте). В пакет кладётся и эскиз (`Order.sketchImage`) из проекта. Счёт на оплату в пакет не входит — выставляется в 1С (05-З3).

**Нумерация (решение владельца — 05-В):** единый сквозной номер года `ПМ2026-NNNNN` (ПМ = Про Мебель, год, NNNNN — сквозная нумерация). Номер договора = номер проекта. БЗ, СП, акты (АВР) и ГТ наследуют этот же номер (хвост «ПМ-26» в шапках не печатается, 05-В1/В2). Номер присваивается в момент генерации (создания проекта) и хранится в проекте; при необходимости отдельной серии для актов/талонов — настраиваемая схема.

## 3. Выбор стека: сравнение вариантов

| Критерий | Python `docxtpl` + `openpyxl` | PHP `PhpWord` + `PhpSpreadsheet` | HTML-шаблоны → PDF |
|---|---|---|---|
| Поддержка .docx-шаблонов с условной логикой | Отлично (Jinja2 внутри docx) | Удовл. (PhpWord без Jinja-условий из коробки) | нет (нужна перевёрстка в HTML) |
| Таблицы xlsx с циклами и объединёнными ячейками | Хорошо (openpyxl: стили, мержи, формулы) | Хорошо | нет |
| Суммы прописью на русском | Библиотеки (num2words ru / своя функция) | своя функция | своя функция (JS/PHP) |
| Юридическая точность к оригиналу | **Высокая** (заполняем оригинальный docx, текст не перепечатывается) | Средняя | Низкая (текст переносится в HTML — риск расхождений) |
| Зависимость от стека CRM | Не зависит (вызывается как модуль/сервис) | Только PHP-CRM | Не зависит |
| Встраивание эскиза (картинки) | docxtpl поддерживает inline-изображения | ограниченно | легко |

**Рекомендация: Python** (`docxtpl` для docx, `openpyxl` для xlsx, рендер прописей — собственная функция по правилам рус. языка). Причины: максимальное сохранение оригинала (заполняются сами .docx-образцы, а не перепечатанные тексты), зрелые библиотеки, не привязан к языку CRM.
**Запасной вариант:** HTML-шаблоны → PDF (LibreOffice headless / WeasyPrint), если нужен только PDF и допустима перевёрстка.
**Интеграция с CRM:** генератор оформляется как отдельный Python-модуль/сервис, вызываемый из CRM (HTTP API или CLI) — стек CRM не важен. Если CRM на PHP — тот же сервис вызывается по HTTP.

## 4. Хранение шаблонов

- **Исходные образцы:** `documents/` (файлы `*_2026.docx/xlsx`) — версионируются (по решению 05-И1 добавлены в git принудительно, в `.gitignore` внесено исключение для `documents/*_2026.docx`).
- **Рабочие шаблоны генератора** (копии образцов, где заглушки заменены плейсхолдерами): отдельная папка `templates/` рядом с генератором; конвертация выполняется **один раз** по «Карте замен» (см. файлы `02_templates/*.template.md`): скрипт ищет в docx точные заглушки (номера «№ ______», даты ««___» ____________ 2026 г.», подчёркивания) и заменяет их на Jinja-конструкции. Тексты без заглушек не трогаются.
- **Спецификация шаблонов** (эта папка): `templates_result/` — реестр, шаблоны-описания, логика, реализация — в git (уже запушено).
- Версионирование шаблонов: обычный git + тег на каждый релиз; в CRM хранится версия шаблона, использованная для каждого проекта (для воспроизводимости).

## 5. Данные и контекст рендера

При создании проекта формируется **JSON-снапшот** (фиксируется на момент генерации и хранится в проекте — поздние изменения карточек не «переписывают» уже выданные документы):

```json
{
  "Client": {"type": "individual", "fullName": "…", "gender": "f", "passport": {"series": "…", "…": "…"}, "regAddress": "…", "phone": "…", "email": "…"},
  "Order": {"number": "ПМ2026-000001", "date": "2026-05-05", "hasAssembly": true, "deliveryAddress": "…",
            "items": [{"name": "…", "size": "…", "materialColor": "…", "qty": 1, "price": 0, "amount": 0, "note": ""}],
            "services": […], "total": 0, "totalWithDiscount": 0, "nds": false, "managerName": "…", "sketchImage": "…"},
  "Doc": {"saleContract": {"number": "ПМ2026-000001", "date": "2026-05-05"}, "blankOrder": {"number": "…"}, "…": "…"}
}
```

Поля контекста — строго по реестру (`01_variables_register.md`); генератор дополнительно валидирует: каждый плейсхолдер шаблона присутствует в контексте (сверка «плейсхолдер ⇄ реестр ⇄ контекст»), отсутствующие обязательные поля приводят к ошибке со списком полей (документ не формируется «полупустым»).

Форматтеры: `rus_date` (««05» мая 2026 г.»), `rus_full_date` (паспортная дата), `fmt_roubles` (разделители тысяч), `fmt_kopeks`, `sum_words` (пропись, рублей/копеек, склонение), карта месяцев (родительный падеж).

## 6. Формирование файлов

1. **docx (ДКП, ДМ, акты, ГТ, памятка, правила):** копия рабочего шаблона → `docxtpl` с контекстом JSON → готовый `.docx`; при необходимости конвертация в PDF (LibreOffice headless `--convert-to pdf`).
2. **xlsx (БЗ, СП):** копия листа-образца → `openpyxl`: заполнение ячеек по «карте листа»; **циклы** (позиции изделий/услуг) — вставка строк с копированием стилей и объединений, пересчёт нумерации; суммы итогов — значением или формулой `=SUM(...)`.
3. **Эскиз** (`Order.sketchImage`): вставка изображения в область эскиза БЗ (пропорции — по размеру области).
4. Суммы прописью и признаки НДС — по правилам реестра № 67–69; по умолчанию «НДС не облагается» (продавец на УСН «доходы-расходы», 05-З1).

## 7. Тестирование и приёмка

- Два эталонных набора демо-данных: **физлицо** (с монтажом и без) и **юрлицо** (+ вариант ИП), в т.ч. случаи: выставочный образец, скидка, частичная передача, претензии при приёмке.
- Проверки: плейсхолдеры не остались незаменёнными (после рендера в тексте нет `{{`/`}}` и исходных заглушек «______» в заполняемых местах); суммы цифрами = прописью; даты в формате оригинала; документы открываются (валидация docx/xlsx); юрлицо-комплект согласован юристом.
